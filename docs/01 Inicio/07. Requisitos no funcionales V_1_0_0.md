| **Versión** | 1.0.0 |

## 1. Objetivo del Documento

Definir los requisitos no funcionales de **EcoLogística Lima** mediante atributos de calidad medibles y verificables, utilizando como referencia el modelo de calidad **ISO/IEC 25010** y la estructura de escenarios de calidad empleada en **arc42**.

Cada requisito se expresa mediante:

- **Fuente:** actor o elemento que origina el estímulo.
- **Estímulo:** evento que afecta al sistema.
- **Entorno:** condición en la que ocurre el estímulo.
- **Artefacto:** componente o parte del sistema afectada.
- **Respuesta:** comportamiento esperado.
- **Medida:** umbral cuantitativo y verificable.

Se evita el uso de términos ambiguos como “rápido”, “seguro”, “eficiente” o “fácil” sin una métrica objetiva asociada.

---

## 2. Criterios Generales

Los requisitos no funcionales definidos en este documento deben cumplir las siguientes características:

1. Ser **medibles**.
2. Ser **verificables mediante pruebas**.
3. Mantener trazabilidad con los objetivos y restricciones del proyecto.
4. No contradecir los requisitos funcionales.
5. Estar alineados con los atributos de calidad de ISO/IEC 25010.
6. Incluir umbrales de aceptación explícitos.
7. Poder ser revisados al cierre de cada iteración.

## 3. Catálogo de Requisitos No Funcionales

### RNF-001: Rendimiento de Generación de Rutas

- **Categoría ISO/IEC 25010:** Eficiencia de desempeño
- **Prioridad:** Alta

| Elemento | Definición |
|---|---|
| **Fuente** | Usuario del área de operaciones |
| **Estímulo** | Solicitud de generación de rutas optimizadas |
| **Entorno** | Operación normal con hasta 150 pedidos y 15 vehículos disponibles |
| **Artefacto** | Motor de optimización de rutas |
| **Respuesta** | El sistema calcula y devuelve una solución válida respetando las restricciones obligatorias |
| **Medida** | Tiempo total de generación **≤ 45 segundos** |

#### Criterio SMART

El sistema deberá generar una solución válida para hasta **150 pedidos y 15 vehículos en un tiempo máximo de 45 segundos**, medido desde el envío de la solicitud hasta la disponibilidad del resultado.

---

### RNF-002: Rendimiento de Re-optimización Dinámica

- **Categoría ISO/IEC 25010:** Eficiencia de desempeño
- **Prioridad:** Alta

| Elemento | Definición |
|---|---|
| **Fuente** | Usuario de operaciones o evento operativo |
| **Estímulo** | Registro de un nuevo pedido, cancelación, accidente, avería o cambio equivalente |
| **Entorno** | Existencia de una planificación activa |
| **Artefacto** | Motor de re-optimización |
| **Respuesta** | El sistema recalcula las rutas afectadas y genera una nueva propuesta |
| **Medida** | Tiempo de re-optimización **< 30 segundos** |

#### Criterio SMART

Ante un cambio operativo que afecte una planificación activa, el sistema deberá producir una nueva propuesta de rutas en **menos de 30 segundos**.

|---|---|
| **Fuente** | Infraestructura de ejecución |
| **Estímulo** | Solicitudes de acceso durante la jornada operativa |
| **Entorno** | Horario diario entre 5:00 AM y 10:00 PM |

| **Respuesta** | El sistema permanece accesible para los usuarios autorizados |

#### Criterio SMART

La plataforma deberá alcanzar una disponibilidad de al menos **99.5% mensual** dentro del horario operativo de **5:00 AM a 10:00 PM**.

|---|---|

| **Estímulo** | Envío de información entre cliente y servidor |

## 6. Estrategia de Verificación

Los requisitos no funcionales serán verificados mediante una combinación de:

- Pruebas de rendimiento.
- Pruebas de carga.
- Pruebas de estrés controladas.
- Pruebas de seguridad.
- Revisión de accesibilidad.
- Pruebas de compatibilidad.
- Pruebas de recuperación.
- Pruebas de autorización.
- Revisión de logs de auditoría.
- Pruebas de integridad transaccional.
- Revisión de documentación.
- Ejecución de pruebas automatizadas.
- Monitoreo de consumo de recursos.

Cada requisito deberá disponer de evidencia verificable antes de considerarse cumplido.

---

## 7. Gestión de Cambios

Los valores definidos en este documento constituyen la línea base inicial de calidad para la versión **1.0.0**.

Si durante el desarrollo se identifica que un umbral necesita ser modificado:

1. Se deberá justificar técnicamente el cambio.
2. Se deberá evaluar su impacto sobre los requisitos funcionales, arquitectura, cronograma y presupuesto.
3. Se deberá registrar la decisión.
4. Se deberá actualizar la versión del documento conforme al esquema de versionamiento del proyecto.
5. Se deberá mantener trazabilidad entre la versión anterior y la nueva.
