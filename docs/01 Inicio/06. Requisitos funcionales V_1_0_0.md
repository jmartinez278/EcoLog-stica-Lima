## 1. Objetivo del Documento

Definir de manera estructurada, atómica y verificable los requisitos funcionales del sistema **EcoLogística Lima**, asegurando que cada requisito describa exclusivamente **qué debe hacer el sistema**, sin introducir decisiones prematuras de diseño o implementación.

Los requisitos funcionales se derivan del Acta de Constitución, la Declaración de la Visión, los supuestos, restricciones e interesados identificados durante la fase de inicio del proyecto.

---

## 2. Marco de Elicitación Holística y Ética

La elicitación de requisitos de **EcoLogística Lima** se plantea desde una perspectiva holística, considerando no solo las necesidades funcionales del negocio, sino también las condiciones operativas, sociales, ambientales y tecnológicas del contexto de distribución urbana en Lima Metropolitana.

### 2.1. Grupos de usuarios considerados

La identificación de necesidades considera a los siguientes grupos:

- **Responsables de operaciones y logística**, quienes requieren planificar, supervisar y ajustar las rutas de distribución.
- **Conductores**, quienes utilizan las rutas asignadas durante la ejecución de las entregas.
- **Clientes finales**, quienes reciben los pedidos dentro de ventanas de tiempo establecidas.
- **Gerencia o patrocinador**, interesado en indicadores de costo, productividad, sostenibilidad y cumplimiento.
- **Equipo de desarrollo y mantenimiento**, responsable de la evolución técnica del sistema.
- **Equipo docente y evaluadores académicos**, responsables de validar el cumplimiento del alcance y los criterios definidos para el PFA.
- **Proveedores externos de mapas, geocodificación o tráfico**, cuya disponibilidad puede afectar determinadas funciones del sistema.
- **Autoridades y comunidad local**, consideradas indirectamente por las restricciones viales, ambientales y de seguridad.

### 2.2. Técnicas de elicitación consideradas

Para obtener, validar y refinar las necesidades del sistema se consideran las siguientes técnicas:

- Revisión documental del caso de negocio y de la consigna académica.
- Análisis del Acta de Constitución y Declaración de la Visión.
- Entrevistas o sesiones simuladas con responsables de operaciones.
- Análisis de escenarios de reparto y ventanas de entrega.
- Revisión de restricciones de tránsito, seguridad, infraestructura y sostenibilidad.
- Prototipado y demostraciones iterativas.
- Validación mediante criterios de aceptación en formato BDD/Gherkin.

### 2.3. Perspectiva glocal

La solución debe responder a objetivos globales de optimización logística y sostenibilidad, pero adaptarse a las condiciones particulares de Lima Metropolitana.

Se consideran especialmente:

- Congestión vehicular variable.
- Direcciones no estandarizadas y uso frecuente de referencias.
- Diferencias en calidad de infraestructura vial.
- Zonas con conectividad limitada.
- Restricciones de seguridad.
- Condiciones climáticas como neblina o baja visibilidad.
- Necesidad de interfaces comprensibles para usuarios con distintos niveles de experiencia tecnológica.
- Uso del español peruano como idioma principal.

### 2.4. Perspectiva ética

La definición de requisitos deberá evitar funcionalidades que generen discriminación, exposición innecesaria de información o decisiones automatizadas sin posibilidad de revisión.

El sistema deberá:

- Minimizar el tratamiento de datos personales.
- Mantener trazabilidad sobre las decisiones de optimización.
- Evitar que la optimización priorice exclusivamente el costo cuando pueda comprometer la seguridad del conductor.
- Considerar tiempos y condiciones razonables de operación.
- Permitir revisión humana de rutas generadas automáticamente.
- Utilizar indicadores ambientales de forma transparente.
- Mantener consistencia de la información ante fallos o interrupciones.

## 3. Catálogo de Requisitos Funcionales

### RF-001: Gestión de Flota

- **Descripción Atómica:** El sistema debe permitir registrar, consultar, actualizar y desactivar vehículos de la flota cuando un usuario autorizado gestione la información vehicular.
- **Prioridad:** Alta

#### Criterios de Aceptación

##### Ruta Gold

**DADO** que un usuario autorizado se encuentra autenticado y dispone de los datos obligatorios de un vehículo  
**CUANDO** registra un nuevo vehículo con información válida  
**ENTONCES** el sistema almacena el vehículo y confirma su registro.

##### Ruta Feliz

**DADO** que existe un vehículo registrado  
**CUANDO** un usuario autorizado actualiza datos permitidos como capacidad, consumo, factor de emisión o disponibilidad  
**ENTONCES** el sistema guarda los cambios y presenta la información actualizada.

##### Ruta Infeliz

**DADO** que un usuario intenta registrar o modificar un vehículo  
**CUANDO** omite datos obligatorios, ingresa valores inválidos o intenta duplicar un identificador único  
**ENTONCES** el sistema rechaza la operación, conserva el estado anterior y muestra los campos que requieren corrección.

---

### RF-002: Gestión de Pedidos

- **Descripción Atómica:** El sistema debe permitir registrar, consultar, actualizar y cancelar pedidos cuando un usuario autorizado gestione las solicitudes de entrega.
- **Prioridad:** Alta

#### Criterios de Aceptación

##### Ruta Gold

**DADO** que un usuario autorizado dispone de los datos obligatorios del pedido  
**CUANDO** registra un pedido con ubicación, carga, volumen, ventana de tiempo y prioridad válidos  
**ENTONCES** el sistema almacena el pedido y lo deja disponible para planificación.

##### Ruta Feliz

**DADO** que existe un pedido pendiente de planificación  
**CUANDO** un usuario autorizado modifica información permitida antes de su ejecución  
**ENTONCES** el sistema actualiza el pedido y utiliza los nuevos datos en la siguiente planificación.

##### Ruta Infeliz

**DADO** que se intenta registrar o actualizar un pedido  
**CUANDO** los datos son incompletos, incompatibles o la ventana de tiempo no es válida  
**ENTONCES** el sistema rechaza la operación y comunica de forma explícita la causa.

---

### RF-003: Generación de Rutas Optimizadas

- **Descripción Atómica:** El sistema debe generar rutas de distribución a partir de los pedidos disponibles, vehículos habilitados y restricciones operativas cuando un usuario autorizado solicite una planificación.
- **Prioridad:** Alta

#### Criterios de Aceptación

##### Ruta Gold

**DADO** que existen pedidos válidos, vehículos disponibles y restricciones operativas definidas  
**CUANDO** el usuario solicita generar una planificación  
**ENTONCES** el sistema produce una propuesta de rutas y asignaciones que respeta las restricciones obligatorias.

##### Ruta Feliz

**DADO** que algunos pedidos presentan prioridades diferentes  
**CUANDO** el usuario solicita la planificación  
**ENTONCES** el sistema genera rutas considerando las prioridades y restricciones aplicables.

##### Ruta Infeliz

**DADO** que no existe capacidad suficiente o algún pedido no puede ser asignado bajo las restricciones vigentes  
**CUANDO** el usuario solicita generar las rutas  
**ENTONCES** el sistema identifica los pedidos no asignables, mantiene una planificación consistente e informa las causas.

---

### RF-004: Visualización de Rutas en Mapa

- **Descripción Atómica:** El sistema debe mostrar en un mapa las rutas generadas, los puntos de entrega y la secuencia de paradas cuando un usuario consulte una planificación.
- **Prioridad:** Alta

#### Criterios de Aceptación

##### Ruta Gold

**DADO** que existe una planificación válida  
**CUANDO** el usuario abre la vista de rutas  
**ENTONCES** el sistema representa la ruta, los vehículos asignados, los puntos de entrega y el orden de las paradas.

##### Ruta Feliz

**DADO** que existen varias rutas activas  
**CUANDO** el usuario selecciona una ruta específica  
**ENTONCES** el sistema muestra únicamente el recorrido y los puntos correspondientes a la selección.

##### Ruta Infeliz

**DADO** que existe una planificación pero no se encuentra disponible la información cartográfica externa  
**CUANDO** el usuario intenta visualizar la ruta  
**ENTONCES** el sistema conserva la planificación, informa la indisponibilidad del mapa y presenta la información textual disponible.

---

### RF-005: Dashboard de Indicadores

- **Descripción Atómica:** El sistema debe presentar indicadores operativos, económicos y ambientales calculados a partir de las rutas y entregas registradas cuando un usuario autorizado consulte el dashboard.
- **Prioridad:** Alta

#### Criterios de Aceptación

##### Ruta Gold

**DADO** que existen rutas y entregas con datos registrados  
**CUANDO** el usuario accede al dashboard  
**ENTONCES** el sistema presenta indicadores de distancia, tiempo, consumo, emisiones, cumplimiento de entregas y ahorro disponibles para el periodo consultado.

##### Ruta Feliz

**DADO** que existen datos correspondientes a diferentes periodos  
**CUANDO** el usuario aplica un filtro temporal permitido  
**ENTONCES** el sistema recalcula y presenta los indicadores correspondientes al periodo seleccionado.

##### Ruta Infeliz

**DADO** que no existen datos suficientes para calcular uno o más indicadores  
**CUANDO** el usuario consulta el dashboard  
**ENTONCES** el sistema muestra los indicadores disponibles e identifica explícitamente aquellos que no pueden calcularse.

---

### RF-006: Generación de Reportes de Sostenibilidad

- **Descripción Atómica:** El sistema debe generar reportes de sostenibilidad a partir de la información registrada de rutas, consumo, costos y emisiones cuando un usuario autorizado solicite un reporte.
- **Prioridad:** Media

#### Criterios de Aceptación

##### Ruta Gold

**DADO** que existen datos válidos para el periodo solicitado  
**CUANDO** el usuario solicita generar un reporte de sostenibilidad  
**ENTONCES** el sistema produce un reporte con indicadores de emisiones, consumo, costos y variaciones respecto de la línea base disponible.

##### Ruta Feliz

**DADO** que existen datos correspondientes a varios periodos  
**CUANDO** el usuario selecciona un rango de fechas específico  
**ENTONCES** el sistema genera el reporte utilizando únicamente la información comprendida en dicho rango.

##### Ruta Infeliz

**DADO** que el periodo solicitado no contiene información suficiente  
**CUANDO** el usuario intenta generar el reporte  
**ENTONCES** el sistema no genera resultados engañosos e informa qué información falta para completar el reporte.

---

### RF-007: Re-optimización Dinámica de Rutas

- **Descripción Atómica:** El sistema debe recalcular una planificación activa cuando se registre un cambio operativo que afecte la ejecución de una ruta.
- **Prioridad:** Alta

#### Criterios de Aceptación

##### Ruta Gold

**DADO** que existe una planificación activa  
**CUANDO** se registra un nuevo pedido, cancelación, accidente, avería u otra incidencia que modifica las condiciones de ejecución  
**ENTONCES** el sistema genera una nueva propuesta de planificación considerando el estado actualizado de la operación.

##### Ruta Feliz

**DADO** que el cambio afecta únicamente una parte de la planificación  
**CUANDO** se solicita la re-optimización  
**ENTONCES** el sistema conserva las asignaciones que continúan siendo válidas y reajusta las que resultan afectadas.

##### Ruta Infeliz

**DADO** que una incidencia provoca que uno o más pedidos ya no puedan ser asignados  
**CUANDO** se ejecuta la re-optimización  
**ENTONCES** el sistema conserva una planificación consistente, identifica los pedidos afectados y comunica la imposibilidad de asignarlos.

---

### RF-008: Gestión de Conductores

- **Descripción Atómica:** El sistema debe permitir registrar, consultar, actualizar y desactivar conductores cuando un usuario autorizado gestione la información del personal de reparto.
- **Prioridad:** Alta

#### Criterios de Aceptación

##### Ruta Gold

**DADO** que un usuario autorizado dispone de los datos obligatorios de un conductor  
**CUANDO** registra al conductor con información válida  
**ENTONCES** el sistema almacena el registro y lo deja disponible para futuras asignaciones.

##### Ruta Feliz

**DADO** que existe un conductor registrado  
**CUANDO** se actualiza su disponibilidad o información permitida  
**ENTONCES** el sistema guarda los cambios y utiliza la nueva condición en futuras asignaciones.

##### Ruta Infeliz

**DADO** que se intenta registrar o actualizar un conductor  
**CUANDO** se ingresan datos obligatorios incompletos o incompatibles  
**ENTONCES** el sistema rechaza la operación y comunica los datos que requieren corrección.

---

### RF-009: Gestión de Clientes y Preferencias de Entrega

- **Descripción Atómica:** El sistema debe permitir registrar y consultar información de clientes, preferencias de entrega y restricciones de acceso cuando un usuario autorizado gestione los datos asociados a una entrega.
- **Prioridad:** Media

#### Criterios de Aceptación

##### Ruta Gold

**DADO** que un usuario autorizado dispone de la información válida de un cliente  
**CUANDO** registra sus datos y preferencias de entrega  
**ENTONCES** el sistema almacena la información y la deja disponible para la planificación de pedidos asociados.

##### Ruta Feliz

**DADO** que un cliente registrado posee una nueva preferencia o restricción de entrega  
**CUANDO** un usuario autorizado actualiza dicha información  
**ENTONCES** el sistema utiliza la información vigente en las futuras planificaciones relacionadas.

##### Ruta Infeliz

**DADO** que se intenta registrar una preferencia o restricción incompatible con los datos del cliente o del pedido  
**CUANDO** el usuario confirma la operación  
**ENTONCES** el sistema rechaza la información inconsistente y explica la causa.

---

### RF-010: Cálculo y Seguimiento de Emisiones y Compensación de Carbono

- **Descripción Atómica:** El sistema debe calcular las emisiones asociadas a las rutas registradas y presentar información de seguimiento ambiental cuando existan datos suficientes de operación.
- **Prioridad:** Media

#### Criterios de Aceptación

##### Ruta Gold

**DADO** que una ruta dispone de distancia recorrida y datos de consumo o factor de emisión del vehículo  
**CUANDO** el sistema procesa los resultados de la operación  
**ENTONCES** calcula y registra la estimación de emisiones correspondiente.

##### Ruta Feliz

**DADO** que existen resultados de varios periodos  
**CUANDO** el usuario consulta el seguimiento ambiental  
**ENTONCES** el sistema permite comparar emisiones y visualizar su evolución respecto de la línea base disponible.

##### Ruta Infeliz

**DADO** que faltan datos necesarios para calcular las emisiones de una ruta  
**CUANDO** el sistema intenta realizar el cálculo  
**ENTONCES** no genera un valor estimado sin fundamento e identifica los datos faltantes.

## 5. Criterios Generales de Calidad de los Requisitos

Todos los requisitos funcionales definidos en este documento deben cumplir los siguientes criterios:

1. **Atomicidad:** cada requisito representa una capacidad funcional claramente identificable.
2. **Claridad:** se evita el uso de términos ambiguos como “fácil”, “rápido”, “adecuado” o “eficiente”.
3. **Verificabilidad:** cada requisito posee criterios de aceptación observables.
4. **Trazabilidad:** los requisitos se derivan del alcance definido en los documentos de inicio del proyecto.
5. **Neutralidad tecnológica:** la descripción funcional especifica el comportamiento esperado sin imponer detalles innecesarios de implementación.
6. **Consistencia:** ningún requisito debe contradecir las restricciones, supuestos u objetivos aprobados.
7. **Orientación al usuario:** cada requisito responde a una necesidad de un actor o proceso identificado.
8. **Mantenibilidad:** la codificación permite relacionar los requisitos con reglas de negocio, requisitos no funcionales, pruebas y componentes de arquitectura en documentos posteriores.

## 6. Estrategia de Validación

Los requisitos serán revisados al cierre de cada iteración mediante:

- Revisión del catálogo de RF.
- Validación de criterios BDD/Gherkin.
- Prototipos o demostraciones funcionales.
- Pruebas de aceptación.
- Matriz de trazabilidad con reglas de negocio.
- Verificación de coherencia con requisitos no funcionales.
- Registro de cambios mediante control de versiones Git.

Cuando un requisito experimente una modificación sustancial, deberá actualizarse el versionamiento del documento conforme al esquema definido para el proyecto.
