## 1. Propósito y Justificación del Proyecto

DistriRápido S.A.C. es un operador logístico ficticio con sede en San Juan de Lurigancho, Lima, que realiza más de **250 entregas diarias** en San Juan de Lurigancho, El Agustino, Santa Anita y Ate.

La operación enfrenta los siguientes problemas principales:

- **Alta congestión vehicular**, especialmente en vías como Av. Próceres de la Independencia y Av. Fernando Belaúnde Terry.
- **Altos costos operativos:** combustible y mantenimiento representan aproximadamente el **35% de los costos totales**.
- **Impacto ambiental:** la flota de 15 camionetas, mayormente diésel, genera aproximadamente **3.5 toneladas de CO₂ mensuales**.
- **Incumplimiento de ventanas de entrega:** aproximadamente **22% de las entregas** se realizan fuera del horario acordado.

El proyecto **EcoLogística Lima** busca diseñar, desarrollar e implementar una plataforma web que optimice las rutas de reparto de última milla mediante metaheurísticas aplicadas al VRPTW y Green VRP, incorporando además criterios económicos, ambientales, operativos y de seguridad.

## 2. Objetivos Medibles (Criterios SMART)

| Dimensión | Objetivo SMART | Meta verificable |
|---|---|---|
| **Alcance** | Desarrollar y entregar, al cierre de la semana 14, un MVP funcional con gestión de pedidos, flota, conductores, optimización de rutas, visualización en mapa, dashboard y reportes. | Implementar y validar al menos el **70% de los requerimientos funcionales RF-01 al RF-07**. |
| **Cronograma** | Completar el proyecto en cuatro iteraciones dentro de un periodo total de 14 semanas. | Entregar los productos previstos al cierre de las semanas 3, 7, 11 y 14. |
| **Costo** | Ejecutar el proyecto sin superar el presupuesto inicial autorizado para el MVP. | Mantener el costo acumulado en **S/ 500,000 o menos**. |
| **Rendimiento** | Asegurar que el motor de optimización responda dentro de los límites definidos. | Generar una solución válida en **≤ 45 s** para hasta 150 pedidos y 15 vehículos, y re-optimizar en **< 30 s**. |
| **Disponibilidad** | Mantener el sistema operativo durante la jornada definida para el servicio. | Alcanzar **99.5% de disponibilidad** entre 5:00 AM y 10:00 PM. |
| **Escalabilidad** | Diseñar una arquitectura preparada para el crecimiento de la operación. | Soportar escalamiento horizontal hasta **1,000 pedidos diarios y 50 vehículos**. |
| **Calidad** | Aplicar estándares de calidad, seguridad y accesibilidad definidos para el proyecto. | Considerar ISO/IEC 25010, OWASP Top 10, WCAG 2.1 AA, Green Software e ISO 14083 en el desarrollo y validación. |

## 3. Requisitos de Alto Nivel

### 3.1. Requerimientos funcionales

- **RF-01 Gestión de Flota:** registro de vehículos, capacidad, consumo, factor de emisión y antigüedad.
- **RF-02 Gestión de Pedidos:** direcciones, GPS, carga, volumen, ventana de tiempo, prioridad y tipo de producto.
- **RF-03 Generación de Rutas Optimizadas:** metaheurística para minimizar distancia, tiempo, combustible, emisiones y penalizaciones.
- **RF-04 Visualización de Rutas en Mapa:** trazado de ruta, puntos de entrega, tiempos y nivel de congestión.
- **RF-05 Dashboard de Indicadores:** métricas de distancia, emisiones, combustible, cumplimiento y ahorro.
- **RF-06 Reportes de Sostenibilidad:** reportes PDF de emisiones, TCO, ahorro y metas ambientales.
- **RF-07 Re-optimización Dinámica:** recálculo de rutas ante nuevos pedidos, cancelaciones, accidentes o averías.
- **RF-08 Gestión de Conductores:** datos personales, licencia, experiencia, disponibilidad y contacto.
- **RF-09 Módulo de Clientes:** preferencias de entrega y restricciones de acceso.
- **RF-10 Plan de Compensación de Carbono:** cálculo de emisiones y propuesta de compensación.

### 3.2. Requerimientos no funcionales principales

- **RNF-01 Rendimiento:** solución válida en máximo 45 segundos y re-optimización en menos de 30 segundos.
- **RNF-02 Seguridad:** medidas alineadas con OWASP Top 10 y protección de datos.
- **RNF-03 Accesibilidad:** WCAG 2.1 nivel AA.
- **RNF-04 Escalabilidad:** hasta 1,000 pedidos diarios y 50 vehículos.
- **RNF-05 Usabilidad:** interfaz sencilla y modo conductor simplificado.
- **RNF-06 Disponibilidad:** 99.5% en horario operativo.
- **RNF-07 Documentación:** documentación técnica, de arquitectura, usuario, administrador y API.

### 3.3. Limitaciones técnicas iniciales

- Backend mediante Python con FastAPI o Django.
- Frontend mediante React.js o Vue.js.
- PostgreSQL como base de datos.
- Leaflet/OpenStreetMap para mapas, con posibilidad de Google Maps API cuando sea justificado.
- Diseño responsive y funcionamiento bajo conexiones de baja velocidad.
- Dependencia parcial de fuentes externas de tráfico con cobertura variable.

## 4. Riesgos Macro

| ID | Riesgo | Impacto probable |
|---|---|---|
| R1 | El algoritmo no alcanza el tiempo de respuesta exigido. | Incumplimiento de RNF-01 y degradación de la experiencia de uso. |
| R2 | Los datos de tráfico presentan baja cobertura o precisión. | Rutas subóptimas, desactualizadas o necesidad de carga manual. |
| R3 | La conectividad de campo es limitada. | Interrupciones del servicio y necesidad de contingencia local. |
| R4 | La complejidad de las metaheurísticas supera la experiencia inicial del equipo. | Retrasos, re-trabajo o reducción del alcance implementado. |
| R5 | El alcance crece por la ampliación de requerimientos. | Presión sobre cronograma y presupuesto. |
| R6 | Cambios o restricciones normativas afectan reglas de negocio. | Ajustes funcionales o técnicos durante el desarrollo. |
| R7 | Las condiciones de seguridad vial o infraestructura reducen las rutas disponibles. | Menor eficiencia de la optimización o necesidad de reglas adicionales. |
| R8 | Dependencia de servicios externos de mapas o tráfico. | Incremento de costo, indisponibilidad o limitaciones de integración. |

## 6. Presupuesto Estimado Inicial

**Presupuesto máximo inicial del MVP: S/ 500,000.**

Este importe se adopta porque forma parte de la restricción económica **RES-05** definida en la consigna del proyecto. En consecuencia, el monto se considera un **techo presupuestal autorizado para el escenario empresarial simulado**, y no implica que el equipo académico deba consumir necesariamente la totalidad del presupuesto.

La estimación contempla el valor económico de recursos humanos especializados, desarrollo de software, optimización algorítmica, servicios cloud, APIs, pruebas, investigación de campo, aseguramiento de calidad, documentación y gestión.

| Categoría | Porcentaje | Monto estimado |
|---|---:|---:|
| Desarrollo de software, integración y metaheurística | 60% | S/ 300,000 |
| Infraestructura cloud, mapas, tráfico y servicios externos | 8% | S/ 40,000 |
| Investigación de campo, levantamiento y preparación de datos | 7% | S/ 35,000 |
| Pruebas, seguridad, accesibilidad y aseguramiento de calidad | 10% | S/ 50,000 |
| Documentación, capacitación y gestión del proyecto | 10% | S/ 50,000 |
| Contingencia | 5% | S/ 25,000 |
| **Total** | **100%** | **S/ 500,000** |

La consigna también establece un **costo operativo anual estimado de S/ 120,000** para mantenimiento y soporte posterior al desarrollo.

### Criterio de control presupuestal

- El presupuesto será revisado al cierre de cada iteración.
- Cualquier desviación deberá analizarse antes de ampliar alcance.
- La contingencia se reservará para riesgos técnicos, integración, datos o infraestructura.
- El Director del Proyecto no podrá modificar el techo presupuestal sin aprobación del nivel de gobernanza correspondiente.
